# 요구사항 분석

## 적용 범위와 제약

사용자가 전달한 과제와 관련 자료를 근거로 구현 전 분석 보고서를 작성한다. 프로젝트의 AGENTS.md를 준수한다.

- 사용자가 명시적으로 구현을 요청하지 않으면 구현을 시작하지 않는다. 분석 완료 자체를 구현 승인으로 간주하지 않는다.
- 과제에 없는 조건이나 데이터를 임의로 가정하지 않는다. 정보가 없으면 미확정으로 표시한다.
- 특정 프로그래밍 언어나 개발 프레임워크를 강제하지 않는다.
- 제안은 확정 요구사항과 구분하며, 답변이 필요한 업무 규칙은 질문으로 남긴다.

## 분석 절차

1. **목표와 제출물 식별**: 해결할 업무 문제, 대상 사용자, 기대 결과, 최종 제출물과 명시된 완료 조건을 정리한다. 관련 프로젝트 구조와 자료는 분석에 필요한 범위에서 확인하고 요구사항의 근거를 기록한다.
2. **요구사항 분류**: 각 항목에 식별자를 부여하고 필수, 권장, 미확정으로 분류한다. 명시된 의무 조건은 필수, 선택적 개선 사항은 권장으로 기록한다. 중요해 보인다는 이유로 필수로 승격하지 않는다. 분류 근거가 부족하거나 조건이 충돌하면 미확정으로 둔다.
3. **기능별 처리 정리**: 입력 데이터와 출처·형식, 출력 데이터와 형식, 처리 규칙, 기능 간 의존성을 연결한다. 필드, 단위, 허용 범위, 누락값 처리 등 제공되지 않은 사항은 미확정으로 남긴다.
4. **모호함과 충돌 식별**: 해석이 여러 개인 표현, 누락된 규칙, 자료 간 충돌을 찾아 해당 요구사항과 영향 범위를 표시한다. 충돌을 임의로 해소하지 않는다.
5. **확인 질문 작성**: 업무 담당자가 결정해야 하는 사항을 구체적인 질문으로 작성한다. 각 질문에 관련 요구사항, 필요한 결정, 답변 전 진행이 제한되는 범위를 연결한다.
6. **우선순위와 최소 범위 제안**: 필수 요구사항과 의존성을 기준으로 구현 순서를 제안하고 최종 제출물에 필요한 최소 기능 범위를 정리한다. 미확정 조건에 의존하는 기능은 결정 이후 진행 대상으로 표시한다. 권장 기능의 연기는 제안으로 명시하고, 필수 기능을 제외한 범위를 완성된 제출물로 제시하지 않는다.
7. **검증 기준과 예외 정리**: 각 필수 기능에 대해 관찰 가능한 완료 기준과 정상·경계·오류 입력의 기대 결과를 정리한다. 누락·잘못된 형식·빈 데이터 등은 해당 기능에 관련된 경우만 다룬다. 기대 동작이 정해지지 않은 예외는 확인 질문과 연결한다. 이 단계의 검증 계획을 테스트 실행 결과로 표현하지 않는다.

## 출력 형식

아래 여섯 항목으로 보고한다. 정보가 없는 항목은 임의로 채우지 말고 미확정 사항과 필요한 확인을 기록한다.

### 과제 핵심 목표

해결할 문제, 대상 사용자, 기대 결과, 최종 제출물과 완료 조건을 요약한다.

### 요구사항 분류표

| ID | 요구사항·기능 | 분류 | 근거 | 입력 데이터 | 출력 데이터 | 처리 규칙·의존성 | 미확정·충돌 사항 |
| --- | --- | --- | --- | --- | --- | --- | --- |

### 확인이 필요한 질문

각 질문에 관련 요구사항 ID, 확인할 결정과 업무 영향, 답변 전 진행 가능한 범위를 적는다. 구현을 막는 질문부터 배치한다. 질문이 없으면 없다고 명시한다.

### 구현 우선순위

기능별 제안 순서, 이유, 선행 조건을 정리하고 최소 기능 범위와 이후 검토할 권장 기능을 구분한다.

### 기능별 검증 기준

| 요구사항 ID·기능 | 완료 기준 | 정상 입력 → 기대 결과 | 경계 입력 → 기대 결과 | 오류 입력·예외 → 기대 결과 | 확인이 필요한 기준 |
| --- | --- | --- | --- | --- | --- |

모든 필수 기능을 포함하고, 경계값과 예외 처리 규칙이 제공되지 않았다면 미확정으로 표시한다.

### 예상 위험 요소

요구사항 누락·충돌, 데이터 확보, 의존성 등 근거가 있는 위험과 그 영향, 필요한 확인 또는 대응 제안을 정리한다. 확인된 사실과 가능성을 구분한다.
